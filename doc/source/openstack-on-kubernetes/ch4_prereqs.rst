4단계. 선행 요소 준비 (네트워크·스토리지)
=========================================

이 단계가 하는 일
-----------------

5단계에서 OpenStack을 올리기 전에 **필요한 준비물을 갖추는 단계**\ 입니다. 요리 전에 재료를 손질하고 도구를 늘어놓는 일과 같습니다.

+------------------------------+-----------------------------------------------------------------------------------------------------------------------+
| 준비물                       | 하는 일                                                                                                               |
+==============================+=======================================================================================================================+
| ``kubectl`` 을 서버에서 쓰기 | 그동안은 cp 노드 안에서만 쓸 수 있었던 명령을 서버(``lab`` 계정)에서 바로 쓰게 합니다.                                |
+------------------------------+-----------------------------------------------------------------------------------------------------------------------+
| Helm 저장소와 플러그인       | **Helm** 은 Kubernetes용 앱 설치 도구이고, OpenStack-Helm이 제공하는 설치 꾸러미(차트)를 받아 올 저장소를 연결합니다. |
+------------------------------+-----------------------------------------------------------------------------------------------------------------------+
| OpenStack-Helm 소스          | 고정한 버전(태그 ``2026.1.0``)의 소스와 설정 파일(values)을 받아 둡니다.                                              |
+------------------------------+-----------------------------------------------------------------------------------------------------------------------+
| 네임스페이스                 | OpenStack 서비스를 담을 ``openstack`` 이라는 칸을 만듭니다.                                                           |
+------------------------------+-----------------------------------------------------------------------------------------------------------------------+
| 노드 레이블                  | "이 노드에는 관리 서비스, 저 노드에는 컴퓨트 서비스를 올려라"를 정하는 표시를 붙입니다.                               |
+------------------------------+-----------------------------------------------------------------------------------------------------------------------+
| 스토리지                     | MariaDB, RabbitMQ 같은 서비스가 **데이터를 저장할 공간**\ 을 Kubernetes가 만들어 주게 합니다.                         |
+------------------------------+-----------------------------------------------------------------------------------------------------------------------+
| 차트 버전 고정               | 설치할 차트 10개의 버전을 정확히 못 박습니다.                                                                         |
+------------------------------+-----------------------------------------------------------------------------------------------------------------------+

.. note::

   이 단계의 **Ingress(외부 노출) 와 MetalLB는 설치하지 않았습니다.** 이유는 아래 "결정과 변경점"에 있습니다.

선행 조건
---------

- 3단계 완료 (노드 4대 ``Ready``, 파드 모두 ``Running``)

.. _1-서버에서-kubectl-쓰기:

1. 서버에서 kubectl 쓰기
~~~~~~~~~~~~~~~~~~~~~~~~

.. code:: bash

   # STAGE 4
   # MANUAL 4
   mkdir -p ~/.kube
   ssh -i ~/.ssh/id_vm_ed25519 kit@192.168.100.10 'sudo cat /etc/kubernetes/admin.conf' > ~/.kube/config
   chmod 600 ~/.kube/config
   kubectl get nodes

노드 4대가 ``Ready`` 로 보이면 됩니다.

.. warning::

   ``~/.kube/config`` 는 클러스터 관리자 권한이 들어 있는 **비밀 파일**\ 입니다. 권한을 ``600`` 으로 하고, **GitHub에 올리지 마세요.**

.. note::

   **TODO:** ``admin.conf`` 의 ``server:`` 주소를 따로 고쳤는지 확인하고 필요하면 이 절에 추가할 것.

.. _2-helm-저장소-플러그인-openstack-helm-소스:

2. Helm 저장소, 플러그인, OpenStack-Helm 소스
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code:: bash

   helm repo add openstack-helm https://tarballs.opendev.org/openstack/openstack-helm
   helm repo update
   helm plugin install https://opendev.org/openstack/openstack-helm-plugin
   git clone --branch 2026.1.0 --depth 1 https://opendev.org/openstack/openstack-helm.git ~/openstack-helm
   git -C ~/openstack-helm rev-parse HEAD
   helm plugin list

- ``rev-parse HEAD`` 는 ``c665eedfa3ae1b76a7e8438fffcb62aefaa30a46`` 이어야 합니다. 받은 소스가 정확히 태그 ``2026.1.0`` 이라는 확인입니다.
- ``helm plugin list`` 에 ``osh 0.1.0`` 이 보여야 합니다.

.. note::

   Helm은 v3.18.4를 씁니다. Helm 4.x는 아직 OpenStack-Helm과의 호환을 확인하지 않았습니다.

.. _3-네임스페이스와-노드-레이블:

3. 네임스페이스와 노드 레이블
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

.. code:: bash

   kubectl create namespace openstack
   kubectl label --overwrite node ctrl-worker openstack-control-plane=enabled openvswitch=enabled
   kubectl label --overwrite node compute-1 compute-2 openstack-compute-node=enabled openvswitch=enabled
   kubectl get nodes -L openstack-control-plane,openstack-compute-node,openvswitch

OpenStack-Helm은 이 레이블을 보고 각 서비스를 어느 노드에 올릴지 정합니다.

+----------------------+--------------------------------------------------------------+-------------------------------+
| 노드                 | 레이블                                                       | 뜻                            |
+======================+==============================================================+===============================+
| ctrl-worker          | ``openstack-control-plane=enabled``, ``openvswitch=enabled`` | 관리 서비스, 가상 스위치      |
+----------------------+--------------------------------------------------------------+-------------------------------+
| compute-1, compute-2 | ``openstack-compute-node=enabled``, ``openvswitch=enabled``  | 컴퓨트 서비스, 가상 스위치    |
+----------------------+--------------------------------------------------------------+-------------------------------+
| cp                   | 없음 (일부러 제외)                                           | Kubernetes 관리 전용으로 유지 |
+----------------------+--------------------------------------------------------------+-------------------------------+

``--overwrite`` 는 이미 있으면 덮어쓴다는 뜻이라 여러 번 실행해도 안전합니다. ``ctrl-worker`` 의 레이블이 모두 붙었는지 한 줄로 확인할 수 있습니다.

.. code:: bash

   kubectl get node ctrl-worker --show-labels | tr ',' '\n' | grep -E 'openstack|openvswitch'
   # openstack-control-plane=enabled
   # openvswitch=enabled

.. _4-차트-버전-고정:

4. 차트 버전 고정
~~~~~~~~~~~~~~~~~

.. warning::

   **Helm 저장소(tarballs)에서 버전을 지정하지 않고 받으면 개발 중인 차트(2026.2 계열)가 설치됩니다.** 저장소에는 2026.1 계열 차트가 32개, 2026.2 계열이 8개 등 129개 버전이 올라 있고, 맨 위(최신)는 개발판입니다. "어제와 오늘 결과가 다르다"의 가장 흔한 원인이므로, 반드시 아래 버전으로 고정하세요.

태그 ``2026.1.0`` 의 커밋 앞 9글자(``c665eedfa``)가 버전 끝에 붙은 차트로 고정합니다.

=========== ===================
차트        고정 버전
=========== ===================
rabbitmq    2025.2.11+c665eedfa
mariadb     2025.2.9+c665eedfa
memcached   2025.2.6+c665eedfa
keystone    2025.2.18+c665eedfa
glance      2025.2.19+c665eedfa
openvswitch 2025.2.11+c665eedfa
libvirt     2025.2.13+c665eedfa
placement   2025.2.16+c665eedfa
nova        2025.2.34+c665eedfa
neutron     2025.2.30+c665eedfa
=========== ===================

.. note::

   차트 이름이 ``2025.2`` 로 시작하는데 태그는 ``2026.1.0`` 인 이유는 확인하지 못했습니다. (태그가 새 주기의 시작점에 붙고 차트 번호는 이전 주기의 마지막 번호로 이어지는 것으로 추정하지만 확인한 것은 아닙니다.) 버전 표에는 **태그, 커밋, 차트 버전을 모두** 적으세요.

차트를 찾을 때 쓴 확인 명령은 다음과 같습니다.

.. code:: bash

   # NOTE 4: 차트 버전 확인
   helm search repo openstack-helm/keystone --versions | grep -E '2026\.1\.' | head -5
   helm search repo openstack-helm/keystone --versions | grep 'c665eedfa'

.. warning::

   ``grep`` 패턴 앞에 공백을 넣으면(``' 2026\.1\.'``) 일치하는 줄이 없어서 "2026.1 차트가 없다"고 잘못 판단하게 됩니다.

.. _5-스토리지-만들기:

5. 스토리지 만들기
~~~~~~~~~~~~~~~~~~

OpenStack-Helm의 서비스(MariaDB, RabbitMQ 등)는 이름이 **``general``** 인 스토리지 클래스를 찾습니다. 3단계 직후의 클러스터에는 스토리지 클래스가 하나도 없어서, 그대로 두면 5단계에서 데이터를 저장하는 파드가 시작하지 못합니다.

공식 문서는 Ceph를 권장하지만, 소규모 실습에서 너무 무거워서 **노드의 디스크를 쓰는 간단한 방식(local-path)** 을 씁니다. Kubespray에 이 옵션이 있어서 설정 두 줄로 켭니다.

.. code:: bash

   F=~/openinfra-lab-kit/kubespray/inventory/openinfra/group_vars/k8s_cluster/addons.yml
   grep -nE '^local_path_provisioner' $F      # 견본에는 enabled: false 줄이 이미 있음

견본 파일에 이미 있는 ``local_path_provisioner_enabled: false`` 를 ``true`` 로 **바꾸고**, 클래스 이름 줄을 추가합니다.

.. code:: yaml

   local_path_provisioner_enabled: true
   local_path_provisioner_storage_class: "general"

.. warning::

   **같은 변수가 파일에 두 번 들어가지 않게 하세요.** 끝에 ``enabled: true`` 를 덧붙이면 견본의 ``false`` 줄과 중복됩니다. (이 가이드에서도 그렇게 해서, 덧붙인 줄을 지우고 견본 줄을 ``true`` 로 고쳤습니다.) ``grep -nE '^local_path_provisioner' $F`` 로 각 변수가 한 번씩만 나오는지 확인하세요.

그다음 3단계의 설치 명령을 다시 실행합니다. 이미 된 작업은 건너뛰고 바뀐 부분만 적용됩니다.

.. code:: bash

   cd ~/kubespray
   time ansible-playbook -i ~/openinfra-lab-kit/kubespray/inventory/openinfra/inventory.ini \
     --become cluster.yml 2>&1 | tee ~/logs/kubespray-cluster-storage-$(date +%m%d-%H%M).txt

.. note::

   **TODO:** 이 재실행의 ``PLAY RECAP`` 과 ``real`` 시간을 기록할 것 (``~/logs/kubespray-cluster-storage-*.txt`` 마지막 20줄).

기대 결과
---------

.. code:: bash

   kubectl get storageclass
   kubectl get pods -A | grep local-path

- 스토리지 클래스 ``general (default)`` 가 보이고, provisioner는 ``rancher.io/local-path`` 입니다.
- ``local-path-provisioner`` 파드가 ``1/1 Running`` 입니다.

+--------------------------+-----------------------------------------------------------------------------------------------------------+
| 항목                     | 값과 의미                                                                                                 |
+==========================+===========================================================================================================+
| ``(default)``            | 기본 클래스. 클래스를 지정하지 않은 요청도 ``general`` 로 만들어집니다.                                   |
+--------------------------+-----------------------------------------------------------------------------------------------------------+
| 회수 정책 ``Delete``     | 볼륨 요청을 지우면 데이터도 같이 지워집니다. 반복 평가에서 깨끗이 정리되는 장점이 있습니다.               |
+--------------------------+-----------------------------------------------------------------------------------------------------------+
| ``WaitForFirstConsumer`` | 파드가 노드에 배치될 때 볼륨이 만들어집니다. 5단계에서 볼륨 요청이 한동안 ``Pending`` 인 것은 정상입니다. |
+--------------------------+-----------------------------------------------------------------------------------------------------------+

확인 방법: 작은 시험 파드
~~~~~~~~~~~~~~~~~~~~~~~~~

스토리지가 실제로 쓰이는지 작은 시험을 합니다. ``general`` 로 1Gi 볼륨을 요청하고, ``ctrl-worker`` 에 고정한 파드가 그 볼륨에 글자를 쓰고 다시 읽어 ``storage-ok`` 를 출력하게 합니다.

.. note::

   **TODO:** 시험 매니페스트(``sc-test``)를 저장소에서 가져와 붙일 것.

.. code:: bash

   kubectl get pod,pvc -n openstack -o wide
   kubectl logs sc-test -n openstack

기대 결과는 파드 ``Completed``, 볼륨 요청 ``Bound`` (1Gi, ``general``, RWO), 로그 ``storage-ok`` 입니다. 이 시험으로 ① 노드 레이블(파드가 레이블이 붙은 노드에서만 실행됨), ② 스토리지 클래스, ③ VM에서 외부 이미지 저장소 접속이 함께 확인됩니다.

**시험이 끝나면 반드시 지웁니다.**

.. code:: bash

   kubectl delete pod,pvc sc-test -n openstack
   kubectl get pod,pvc -n openstack          # No resources found 이면 정리됨

결정과 변경점
-------------

+-------------------------------+---------------------------------------------------------+-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| 항목                          | 결정                                                    | 이유와 한계                                                                                                                                                                                                                                                                                                                   |
+===============================+=========================================================+===============================================================================================================================================================================================================================================================================================================================+
| Ingress, MetalLB, Gateway API | **설치하지 않음** (5단계에서 최종 확정)                 | 이 태그의 차트 10개 모두 ``kind: Ingress`` 템플릿이 0개이고, 외부 노출을 차트 밖에서 지정하는 방식(``extraObjects``)을 지원합니다. 검증 범위(L2)에서는 서비스 간 내부 연결만 쓰므로 필요하지 않다고 판단했습니다. Kubespray v2.31.0이 ingress-nginx 지원을 제거한 것도 영향이 없습니다. (계획 기본안 "MetalLB 사용"에서 변경) |
+-------------------------------+---------------------------------------------------------+-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| 스토리지                      | Ceph 대신 local-path (``general``)                      | 소규모 실습에 단순합니다. 한계: 볼륨이 **한 노드의 디스크에만** 있어서 그 노드가 죽으면 데이터가 사라집니다.                                                                                                                                                                                                                  |
+-------------------------------+---------------------------------------------------------+-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| 차트 설치 방식                | 저장소 차트를 버전 지정으로 설치 (소스 직접 빌드 안 함) | 고정한 커밋과 같은 차트가 저장소에 있어서 재현됩니다. 의존 차트 빌드가 필요한지는 5단계에서 확인합니다.                                                                                                                                                                                                                       |
+-------------------------------+---------------------------------------------------------+-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+

이 단계에서 겪은 오류와 주의사항
--------------------------------

+---+-----------------------------------------------------+-------------------------------------------------------------------------------+------------------------------------------------------------------------------+
| # | 증상                                                | 원인                                                                          | 해결                                                                         |
+===+=====================================================+===============================================================================+==============================================================================+
| 1 | 차트를 버전 없이 받으면 2026.2 개발판이 설치될 상황 | 저장소 최신 항목이 개발판                                                     | 커밋 해시가 붙은 버전으로 10개 모두 고정                                     |
+---+-----------------------------------------------------+-------------------------------------------------------------------------------+------------------------------------------------------------------------------+
| 2 | 클러스터에 스토리지 클래스가 하나도 없음            | Kubespray 기본값은 local-path가 꺼져 있음                                     | ``addons.yml`` 에서 켜고 클래스 이름을 ``general`` 로 지정, Kubespray 재실행 |
+---+-----------------------------------------------------+-------------------------------------------------------------------------------+------------------------------------------------------------------------------+
| 3 | ``addons.yml`` 에 같은 변수가 두 번 있음            | 견본의 ``false`` 줄을 두고 끝에 ``true`` 를 덧붙임                            | 덧붙인 줄을 지우고 견본 줄을 ``true`` 로 수정                                |
+---+-----------------------------------------------------+-------------------------------------------------------------------------------+------------------------------------------------------------------------------+
| 4 | 일부 차트에 ``2026.1-ubuntu_noble.yaml`` 이 없음    | openvswitch는 ``ubuntu_noble.yaml``, memcached는 해당 이름의 설정 파일이 없음 | 어느 파일이 적용되는지는 플러그인으로 확인 (5단계에서 확정)                  |
+---+-----------------------------------------------------+-------------------------------------------------------------------------------+------------------------------------------------------------------------------+

.. warning::

   **이미지 고정은 아직 끝나지 않았습니다 (5단계 전에 정해야 함).** 차트를 렌더링해 보니 이미지 19종 중 일부가 ``latest-ubuntu_noble``, ``latest-ubuntu_jammy`` 같은 ``latest-`` 태그를 씁니다 (``kubernetes-entrypoint`` 65회, ``openvswitch``, ``mariadb`` 등). ``latest`` 태그는 같은 이름 아래 새 이미지가 올라올 수 있어서, 일관성 평가(같은 구축을 여러 번 해서 비교)의 전제가 흔들립니다. ``keystone`` 은 ``2026.1`` 이미지와 ``2025.1`` 이미지가 섞여 있고, ``placement`` 에는 ``jammy`` (Ubuntu 22.04)용 이미지도 있습니다. 모든 이미지를 **다이제스트(``@sha256:...``)** 로 고정하는 방식을 5단계 전에 정합니다.

.. note::

   - ``ceph-config-helper`` 이미지가 렌더링에 포함되지만 Ceph를 쓰지 않으므로 실제로는 쓰이지 않을 것으로 추정합니다. (Glance의 저장 방식을 ``pvc`` 로 지정하면 확인됩니다.)
   - ``helm template`` 으로 열 개 차트를 렌더링한 결과 오류가 없었습니다. (``+c665eedfa`` 가 들어간 버전 문자열도 Helm이 받아들였습니다.)
   - 노드 레이블 확인 출력의 마지막 줄이 잘려 보이면 붙여 넣는 과정의 문제일 수 있으니 ``--show-labels`` 로 따로 확인하세요.

7단계. Horizon에 접속하여 인스턴스 만들기
==========================================================================================

이 단계에서 하는 일
------------------------------------------------------------------------------------------

Horizon은 웹 브라우저에서 OpenStack을 사용하는 관리 화면입니다.
인스턴스는 OpenStack으로 만든 가상 머신입니다. 앞서 Terraform으로 만든 네 대의
Kubernetes 노드 VM과 구분합니다. 여기서는 노드 VM 위에서 동작하는 OpenStack에
접속하여 사용자용 인스턴스를 만들고 상태를 확인합니다.

2026년 11월 3~4일 수동 구축에서 명령으로 만든 ``demo-vm1`` 과
Horizon에서 만든 ``demo-vm2`` 가 모두 실행되는 것을 확인했습니다.
아래 안내는 그 기록을 바탕으로 정리한 실습 절차이며, 원본 명령 이력을 그대로
옮긴 것은 아닙니다. 화면의 메뉴 이름은 언어와 Horizon 버전에 따라 다를 수 있습니다.

시작 전에 확인하기
------------------------------------------------------------------------------------------

0~6단계를 마치고 OpenStack API와 인증이 동작해야 합니다.
Horizon은 기존 11개 릴리스 이후에 추가로 설치했습니다.
기록된 Horizon 차트 버전은 ``2025.2.10+c665eedfa`` 이며 설치 직후 리비전은 1입니다.
리비전은 Helm 설정을 설치하거나 변경한 이력 번호입니다.

Ubuntu 호스트에서 다음 상태를 확인합니다.

.. code-block:: bash

   helm status horizon -n openstack
   kubectl get pods -n openstack -o wide
   kubectl get service horizon-int -n openstack

Horizon 릴리스가 있고 관련 Pod의 컨테이너가 준비되어 있어야 합니다.
이 환경에서는 Horizon Pod가 ``1/1 Running`` 이고 ``horizon-int`` 서비스의
80번 포트로 접속했습니다. 릴리스가 없다면 팀에서 최종 ``values-horizon.yaml`` 과
함께 적용한 추가 values 및 설치 명령을 받아 :doc:`ch5_openstack` 의 방식으로
먼저 설치합니다. PDF에는 해당 설정 파일의 전문이 없으므로 기본값만으로
같은 구성이 재현된다고 가정하지 않습니다.

이 실습에서 사용할 자원은 다음과 같습니다. 이미 있으면 설정을 확인하고 재사용하며,
없으면 로그인 후 아래의 이미지·플레이버·네트워크 생성 절차를 진행합니다.
이미지는 가상 머신이 부팅할 운영체제 파일이고, 플레이버는 CPU·메모리·디스크 크기의
묶음입니다. 네트워크와 서브넷은 인스턴스가 사용할 내부 통신망과 주소 범위입니다.

.. list-table:: 사용할 자원
   :header-rows: 1

   * - 종류
     - 이름 또는 값
   * - 부팅 이미지
     - cirros-0.6.2, 상태 active
   * - 플레이버
     - m1.tiny: vCPU 1개, RAM 512 MB, 루트 디스크 1 GB
   * - 네트워크
     - demo-net
   * - 서브넷
     - demo-subnet, 10.10.10.0/24

6단계의 1 MB 시험용 파일은 부팅 이미지가 아닙니다. 여기서는 실제 CirrOS 이미지를
사용합니다. 최종 PDF에 이미지 주소와 플레이버 사양, 화면에서 자원을 만드는
방법이 추가되어 아래에 반영했습니다.

1. Ubuntu 호스트에서 Horizon 연결 열기
------------------------------------------------------------------------------------------

Windows의 첫 번째 터미널에서 Ubuntu 호스트로 SSH 접속합니다.
``서버주소`` 는 팀에서 받은 실제 주소로 바꿉니다.

.. code-block:: powershell

   ssh lab@서버주소

접속한 Ubuntu 호스트에서 다음 명령을 실행합니다.

.. code-block:: bash

   kubectl -n openstack port-forward --address 127.0.0.1 svc/horizon-int 8080:80

이 명령은 호스트의 8080번 포트로 들어온 요청을 Horizon 서비스의 80번 포트로
전달합니다. ``Forwarding from 127.0.0.1:8080`` 이 보이면 이 터미널을 켜 둡니다.
명령이 계속 실행되는 것은 정상입니다. ``Ctrl+C`` 를 누르면 연결이 닫힙니다.

2. Windows에서 SSH 터널 열기
------------------------------------------------------------------------------------------

Windows에서 두 번째 PowerShell 터미널을 새로 엽니다. Ubuntu에 접속한 첫 번째
터미널에 입력하는 명령이 아닙니다.

.. code-block:: powershell

   ssh -N -L 127.0.0.1:8080:127.0.0.1:8080 lab@서버주소

SSH 터널은 내 PC의 요청을 SSH 연결을 통해 서버에 전달합니다.
``-N`` 은 서버 명령창을 열지 않고 연결만 유지하는 옵션입니다.
접속 후 출력이 없어도 오류가 없다면 이 터미널을 켜 둡니다.

.. code-block:: text

   내 PC 브라우저 127.0.0.1:8080
       → SSH 터널
       → Ubuntu 호스트 127.0.0.1:8080
       → kubectl port-forward
       → Horizon 서비스 80번 포트

두 연결이 모두 실행 중이어야 합니다. 이 방법은 SSH를 통한 실습용 접속이며
Horizon을 공인 주소로 직접 공개하는 구성은 아닙니다.

3. 브라우저에서 로그인하기
------------------------------------------------------------------------------------------

Windows 브라우저 주소창에 ``http://127.0.0.1:8080`` 을 입력합니다.
기록에서는 첫 요청이 로그인 화면으로 이동했고, 로그인 페이지가 정상 응답했습니다.

.. list-table:: 기록에서 사용한 로그인 항목
   :header-rows: 1

   * - 항목
     - 입력할 값
   * - Domain
     - Default
   * - User Name
     - admin
   * - Password
     - 해당 환경의 관리자 비밀번호

비밀번호는 팀의 비공개 경로로 전달받습니다. 직접 관리하는 실습 환경에서
확인이 필요한 경우 Ubuntu 호스트의 별도 터미널에서 다음 명령을 사용할 수 있습니다.
이 명령은 비밀번호를 화면에 출력하므로 화면 공유·녹화 중에는 실행하지 않으며
출력값을 문서나 Git에 붙여 넣지 않습니다.

.. code-block:: bash

   kubectl -n openstack get secret keystone-keystone-admin -o jsonpath='{.data.OS_PASSWORD}' | base64 -d
   echo

출력이 없거나 Secret이 없다는 오류가 나면 해당 환경의 Secret 이름과 인증 구성을
관리자에게 확인합니다. ``Default`` 와 ``admin`` 역시 다른 환경에서는 다를 수 있습니다.

4. 부팅 이미지 등록하기
------------------------------------------------------------------------------------------

Horizon 상단에서 실습할 프로젝트를 선택합니다. 이후 이미지와 네트워크, 인스턴스는
같은 프로젝트에서 준비합니다. 이미 같은 이름의 자원이 있으면 상세 설정을 확인하고
재사용합니다. 이름만 같은 자원을 중복 생성하면 나중에 구분하기 어렵습니다.

#. Windows 브라우저에서 `CirrOS 0.6.2 이미지 다운로드
   <https://download.cirros-cloud.net/0.6.2/cirros-0.6.2-x86_64-disk.img>`_ 를 열어
   ``cirros-0.6.2-x86_64-disk.img`` 파일을 내 PC에 저장합니다. 약 20 MB 크기입니다.
#. Horizon에서 **프로젝트 → Compute(컴퓨트) → 이미지 → 이미지 생성** 을 엽니다.
#. 이름은 ``cirros-0.6.2``, 이미지 소스는 내려받은 파일로 지정합니다.
#. 이미지 포맷은 **QCOW2** 를 선택하고 생성합니다. 파일 확장자는 ``.img`` 여도
   이 이미지의 디스크 형식은 QCOW2입니다.
#. 업로드가 끝나고 상태가 **Active(활성)** 인지 확인합니다.

이미지 파일은 SSH 터널을 거쳐 서버에 올라가므로 시간이 걸릴 수 있습니다.
업로드 중에는 두 터미널의 연결을 유지합니다. PDF에는 이미지 체크섬 검증 결과가
없으므로 이 문서에서 검증 완료로 기록하지 않습니다.

5. 플레이버 만들기
------------------------------------------------------------------------------------------

플레이버는 인스턴스에 배정할 자원의 크기입니다. 예를 들어 ``m1.tiny`` 를 선택하면
아래에 등록한 CPU·메모리·디스크 크기가 적용됩니다. 이름 자체가 사양을 보장하는
것은 아니므로 기존 플레이버를 사용할 때도 값을 확인합니다.

관리자 계정으로 **관리 → Compute(컴퓨트) → 플레이버 → 플레이버 생성** 을 엽니다.

.. list-table:: 실습용 플레이버
   :header-rows: 1

   * - 항목
     - 값
   * - 이름
     - m1.tiny
   * - VCPU
     - 1
   * - RAM (MB)
     - 512
   * - 루트 디스크 (GB)
     - 1

나머지 항목은 기본값으로 두고 생성합니다. 관리 메뉴가 보이지 않으면 해당 계정의
권한을 확인합니다. 이 작은 사양은 CirrOS 실습용이며 일반 서버의 권장 사양은 아닙니다.

6. 내부 네트워크 만들기
------------------------------------------------------------------------------------------

#. **프로젝트 → 네트워크 → 네트워크 → 네트워크 생성** 을 엽니다.
#. **네트워크** 탭의 이름에 ``demo-net`` 을 입력합니다.
#. **서브넷** 탭에 이름 ``demo-subnet``, 네트워크 주소 ``10.10.10.0/24`` 를 입력합니다.
   IPv4 주소 범위이며, 게이트웨이 입력란은 PDF 안내대로 비워 둡니다.
   입력란을 비우는 것과 게이트웨이 사용을 해제하는 것은 다르므로 혼동하지 않습니다.
#. **서브넷 세부 정보** 탭은 기본값을 사용하고, **DHCP 사용** 이 켜져 있는지
   확인한 뒤 생성합니다. DHCP는 인스턴스에 내부 IP 주소를 자동으로 배정합니다.
#. 생성된 네트워크와 서브넷의 이름·주소 범위·DHCP 설정을 확인합니다.

이 네트워크는 내부 통신용입니다. 게이트웨이 주소가 표시되더라도 외부 네트워크와
라우터 연결을 구성한 것은 아닙니다. 이 절차에는 Floating IP를 통한 외부 접속이
포함되지 않습니다. 인스턴스 간 실제 통신 역시 보안 그룹 등 설정에 따라 별도 확인합니다.

7. Horizon에서 인스턴스 만들기
------------------------------------------------------------------------------------------

로그인한 뒤 준비한 이미지와 네트워크를 사용할 프로젝트를 선택합니다.
아래에서는 과거 검증 기록과 맞춰 Horizon 생성 인스턴스를 ``demo-vm2`` 로
표기합니다. 최종 PDF의 화면 실습 예시는 ``demo-vm1`` 이지만, 같은 PDF의 과거
결과 표는 CLI 생성 ``demo-vm1`` 과 Horizon 생성 ``demo-vm2`` 를 구분합니다.
이름은 사용자가 정하는 값이므로 새 실습에서는 기존 자원과 구분되는 이름을 쓰면 됩니다.

#. **Project → Compute → Instances** (프로젝트 → 컴퓨트 → 인스턴스)를 엽니다.
#. **Launch Instance** (인스턴스 시작)를 누릅니다.
#. 이름을 ``demo-vm2``, 개수를 1로 지정합니다. 같은 이름의 실습 인스턴스가
   이미 있으면 결과를 구분할 수 있도록 새 이름을 사용합니다.
#. 부팅 소스는 이미지로 선택하고 ``cirros-0.6.2`` 를 지정합니다.
   이 기록에는 Cinder 볼륨 서비스 설치가 없으므로 새 볼륨을 만드는 방식은 선택하지 않습니다.
   해당 옵션이 보이면 **Create New Volume** 을 **No** 로 선택합니다.
#. 플레이버에서 ``m1.tiny``, 네트워크에서 ``demo-net`` 을 선택 목록에 추가합니다.
#. 보안 그룹과 키 페어는 팀의 실습 설정에 맞게 확인합니다. PDF에는 이 두 항목의
   구체적인 선택값은 없고, 최종 안내는 나머지 탭을 기본 상태로 두도록 설명합니다.
   이 실습에서도 기본 상태를 확인하고 진행합니다. 인스턴스 생성과 SSH 접속 검증은 구분하며,
   이 절차만으로 SSH 접속까지 준비되었다고 판단하지 않습니다.
#. 선택한 내용을 확인하고 **Launch Instance** 를 누릅니다.

목록에서 상태가 ``Active``, 전원 상태가 ``Running`` 으로 바뀌는지 확인합니다.
오류 상태가 되면 인스턴스 상세 화면의 오류 메시지와 :doc:`ch8_troubleshooting` 을
확인합니다. 생성 버튼을 반복해서 누르기보다 기존 요청의 결과부터 확인합니다.

8. 실행 결과 확인하기
------------------------------------------------------------------------------------------

먼저 Horizon 목록에서 상태 **Active**, 전원 상태 **Running** 을 확인합니다.
인스턴스 이름을 누르고 **로그** 탭에서 부팅 로그를 읽습니다. ``login:`` 프롬프트는
운영체제가 로그인 입력을 기다리는 단계까지 부팅됐다는 근거입니다. 이 화면을 본 것만으로
실제 로그인이나 네트워크 통신까지 성공했다고 판단하지 않습니다.

Ubuntu 호스트의 별도 터미널에서는 6단계의 ``osc`` Pod를 통해 다음 명령으로도
상태와 부팅 로그를 확인할 수 있습니다. 이는 Horizon 화면 확인의 보조 방법입니다.
다른 이름으로 만들었다면 마지막 인스턴스 이름도 바꿉니다.

.. code-block:: bash

   kubectl -n openstack exec osc -- openstack server list
   kubectl -n openstack exec osc -- openstack server show demo-vm2
   kubectl -n openstack exec osc -- openstack console log show demo-vm2

``ACTIVE`` 는 인스턴스 실행 상태입니다. 실제 운영체제 부팅과 주소 할당은
콘솔 로그도 함께 확인해야 합니다. 콘솔 로그를 읽는 것은 콘솔에 접속해
사용자 이름과 비밀번호로 로그인한 것과 다릅니다.

.. list-table:: 11월 3~4일 수동 구축에서 확인한 결과
   :header-rows: 1

   * - 항목
     - 기록된 결과
   * - demo-vm1
     - CLI로 생성, compute-1에서 ACTIVE, 콘솔 로그에 login 프롬프트
   * - demo-vm1 내부 주소
     - VXLAN 포트 수정 후 DHCP 로그에서 leased 10.10.10.51 확인
   * - demo-vm2
     - Horizon으로 생성, 화면에서 Active / Running 및 10.10.10.90 확인
   * - Horizon
     - Default 도메인의 admin 로그인, 인스턴스 목록 조회와 생성 성공

위 IP는 당시 할당된 값입니다. 다시 생성하면 달라질 수 있으며 직접 고정해서
입력할 값이 아닙니다. ``demo-vm2`` 도 같은 방식으로 부팅 로그와 DHCP를 확인해
새 실습 결과를 기록합니다. 원본의 DHCP 임대 로그는 ``demo-vm1`` 에 대한 기록입니다.

내부 네트워크에서 해결한 문제
------------------------------------------------------------------------------------------

처음에는 인스턴스가 ACTIVE여도 내부에서 DHCP 주소를 받지 못했습니다.
이 환경에서 Calico와 Neutron의 VXLAN이 UDP 4789 포트를 함께 사용한 것이
문제였습니다. VXLAN은 가상 네트워크의 데이터를 다른 노드로 전달하는 방식입니다.
Neutron의 VXLAN 포트를 4790으로 바꾼 뒤 임대 주소를 확인했습니다.
관련 설정과 점검 순서는 :doc:`ch8_troubleshooting` 에 정리했습니다.

실습을 마칠 때와 검증 범위
------------------------------------------------------------------------------------------

발표나 후속 확인에 필요한 자원은 팀과 보존 여부를 정합니다. 삭제할 때는
이번에 만든 인스턴스와 연결 자원만 식별하여 정리합니다. 브라우저에서 로그아웃하고,
두 터미널의 연결은 각각 ``Ctrl+C`` 로 종료합니다.

이번 기록은 첫 수동 구축에서의 로그인·인스턴스 생성·내부 DHCP 확인입니다.
Floating IP를 이용한 외부 통신, 인스턴스 콘솔에 직접 로그인하기,
포트 수정 후 메타데이터 응답 재확인, 호스트 재부팅과 새 서버 반복 구축은
확인 완료 항목에 포함하지 않습니다. 자동화 키트 전체의 재현 성공과도 구분합니다.

.. _verification:

검증과 상태 수집 (6단계)
==========================================================================================

이 장을 읽기 전에
------------------------------------------------------------------------------------------

이 단계는 서비스가 설치되어 있다는 사실을 넘어 실제 요청을 처리하는지 확인합니다.
인증 토큰 발급, 시험용 이미지와 네트워크 생성 등을 수행하고 결과를 저장합니다.
검증 명령은 Ubuntu 호스트의 구현 저장소 최상위에서 실행합니다.
검증 성공은 아래 검사 항목이 통과했다는 뜻이며 모든 OpenStack 기능이 확인됐다는 뜻은 아닙니다.


배포 점검 후 API 기능과 비교용 최종 상태를 확인합니다.
``make stage-6`` 는 서비스 검증에 이어 상태 수집을 실행합니다.
``make deploy`` 에도 이 단계가 포함되어 있으므로 전체 배포가 성공했다면
같은 검증을 바로 다시 실행할 필요는 없습니다. ``make verify`` 대상은 없습니다.

.. note::

   이 장은 코드에 구현된 검사와 실행 방법을 설명합니다.
   해당 커밋으로 실제 서버의 전체 구축·검증이 성공했다는 보고서는 아닙니다.
   실행 후 종료 코드와 로그로 결과를 기록합니다.

6단계 실행과 저장 위치
------------------------------------------------------------------------------------------

5단계까지 완료한 환경에서 다음 명령을 실행합니다.

.. code-block:: bash

   make stage-6

서비스 검증은 ``logs/evaluation/verify``, 상태 수집은
``logs/evaluation/final-state`` 에 결과 파일을 기록합니다.
서비스 검증이 실패하면 Make가 중단되어 다음 상태 수집은 실행되지 않습니다.
이 경로는 실행 번호별로 자동 분리되지 않으므로 이전 결과를 별도 보관합니다.

회차별 폴더를 직접 지정하거나 각 작업을 따로 실행하려면 아래 명령을 사용합니다.
검증의 테스트 자원 생성·삭제가 다시 수행되므로 단순히 로그를 복사하기 위해
재실행하지는 않습니다.


검증에 사용하는 연결 방식
------------------------------------------------------------------------------------------

API는 프로그램이 서비스 기능을 요청하는 접속 창구입니다.
port-forward는 클러스터 안의 서비스에 호스트의 로컬 포트를 연결하는 기능입니다.
예를 들어 ``127.0.0.1`` 은 지금 명령을 실행하는 호스트 자신을 가리킵니다.
이 방식의 API 시험은 외부 인터넷에서 서비스에 접속할 수 있다는 검증과 다릅니다.

토큰은 인증 후 API 요청에 사용하는 정보이며, Kubernetes Secret에서 접속 설정을 읽습니다.
종료 코드 0은 해당 스크립트의 성공을 뜻하고, 0이 아닌 값은 실패 여부를 확인해야 한다는 뜻입니다.

서비스 동작 검증
------------------------------------------------------------------------------------------

.. code-block:: bash

   bash stage6/verify-services.sh logs/run-01/verify

``run-01`` 은 실제 배포 기록 번호와 맞추고 회차별로 다른 폴더를 사용합니다.
직접 실행할 때 인자를 생략하면 ``logs/verify`` 를 사용합니다.
Makefile을 통한 실행은 위에 설명한 ``logs/evaluation/verify`` 를 명시적으로 전달합니다.
스크립트는 Kubernetes Secret에서 인증 정보를 읽고 로컬 port-forward를 통해 API에
접속합니다. OpenStack CLI는 ``~/venv-openstack/bin/openstack`` 을 사용합니다.

.. list-table:: 검사 내용
   :header-rows: 1

   * - 서비스
     - 구현된 검사
   * - Keystone
     - API 응답과 토큰 발급
   * - Glance
     - 작은 테스트 데이터를 이미지로 등록·업로드하고 active 확인 후 삭제
   * - Neutron
     - 테스트 네트워크 생성·조회·삭제, 등록된 에이전트의 alive와 admin_state_up
   * - Nova
     - nova-compute 두 개 및 하이퍼바이저 두 개의 up/enabled
   * - Placement
     - 자원 제공자 두 개

Glance에 넣는 데이터는 부팅 가능한 OS 이미지가 아닙니다.
Neutron 네트워크 상태는 출력하지만 특정 상태값과 일치하는지 검사하지는 않습니다.
검증 과정은 이미지와 네트워크를 실제로 생성·삭제하며, 종료 시 남은 테스트 자원과
port-forward 정리를 시도합니다. 실패 후에는 잔여 자원도 확인합니다.

로컬 포트 15000, 19292, 19696, 18774, 18778을 사용하므로 다른 프로세스와 겹치지
않아야 합니다. 상태 수집 스크립트와 동시에 실행하지 않습니다.

최종 상태 수집
------------------------------------------------------------------------------------------

.. code-block:: bash

   bash stage6/collect-state.sh logs/run-01/final-state

앞의 서비스 검증이 성공한 것을 확인한 뒤 상태 수집을 실행합니다.
노드, Pod 상태별 개수, Helm 릴리스, 컨테이너 이미지, OpenStack 서비스와
엔드포인트, Nova 컴퓨트 서비스, Placement 자원 제공자 정보를 파일로 남깁니다.
이미지 목록은 Pod 명세의 이미지 문자열이며 실제 실행 이미지 digest를 모두 검증한
결과와 동일하지 않습니다.

.. note::

   ``kubernetes-nodes.txt`` 의 STATUS는 조건의 종류를 출력합니다.
   ``Ready`` 라는 문자열만으로 True 여부를 판단할 수 없습니다.
   실제 노드 상태는 ``kubectl get nodes`` 와 3단계 사후 점검으로 확인하세요.

재현 검증 기록
------------------------------------------------------------------------------------------

회차별로 구현 커밋, 서버 환경, 시작·종료 시각, 실패 단계, 추가 조치, 각 스크립트의
종료 코드와 로그를 남깁니다. 상태 수집 성공과 기능 검증 성공을 구분합니다.
새 환경 반복 구축, 재부팅, 사용자 인스턴스 부팅, Floating IP, Horizon 로그인은
해당 시험을 실제 수행한 뒤 결과를 추가합니다.

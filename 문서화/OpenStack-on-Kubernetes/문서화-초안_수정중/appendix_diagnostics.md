# 부록 D. 진단 로그 수집과 새 머신 재현 검증

서버 환경 문제(권한, 보안 장치, 방화벽 등)는 **다른 서버에서 똑같이 재현되지 않는 경우가 많습니다.**
그래서 이 가이드는 두 가지를 목표로 합니다.

1. 문제가 생겼을 때 **원인을 추정하지 않고 로그로 확정**한다. (그리고 그 로그를 문서에 남긴다.)
2. 지금까지 한 구축을 **새 머신에서 자동화 코드만으로 처음부터 끝까지** 돌려 문제없이 끝나는지 확인한다.

같은 문제를 겪는 사람이 "내 로그가 이것과 같은가?"를 비교해 바로 해결할 수 있게 쓰는 것이 방향입니다.

## 1. 실패했을 때 먼저 할 일

고치기 전에 **증거부터 수집**합니다. 고친 뒤에는 실패 상태가 사라져 로그를 다시 얻기 어렵습니다.

```bash
sudo bash scripts/collect-diag.sh        # 현재 폴더에 diag-<시각>.tar.gz 생성
```

- 시스템을 바꾸지 않는 읽기 전용 스크립트입니다. (`scripts/collect-diag.sh`)
- 모으는 것: OS·버전, AppArmor 상태와 거부 로그, 디스크 경로·소유권, libvirt/QEMU 로그, 네트워크·시간 동기화, 쿠버네티스 상태.
- 공인 IP, 토큰, 개인키 줄은 자동으로 가립니다. 그래도 **올리기 전에 직접 훑어보세요.**

> [!WARNING]
> 자동 가림은 완벽하지 않습니다. 공개 저장소나 이슈에 첨부하기 전에 `diag-*/` 안의 파일을 눈으로 확인하세요.

## 2. "VM 시작 `Permission denied`" 판별 순서

원인 후보는 크게 둘입니다. **둘 중 어느 쪽인지 로그로 구분**해야 맞는 해결을 고릅니다.

| 후보 | 의미 | 확인 방법 |
|---|---|---|
| A. AppArmor가 막음 | VM 디스크 경로가 허용 목록에 없음 | 거부 로그에 `apparmor="DENIED"` 와 경로가 찍힘 |
| B. 파일 소유권·권한 | 디스크 파일/폴더를 `libvirt-qemu:kvm` 이 못 읽음 | `namei -l <경로>` 에서 한 단계라도 접근 불가, 소유자 불일치 |

```bash
# A. AppArmor 거부 로그 (아래 중 어딘가에 찍힙니다)
sudo journalctl -k --no-pager | grep -i denied
sudo dmesg | grep -i apparmor
sudo grep -i 'apparmor="DENIED"' /var/log/audit/audit.log /var/log/syslog 2>/dev/null
sudo aa-status                                   # 켜져 있는지, libvirt 프로필이 있는지

# B. 경로와 소유권
namei -l /var/lib/libvirt/images                 # 경로 중간 폴더마다 권한 확인
ls -l /var/lib/libvirt/images
```

해석 요령:

- 거부 로그에 **경로가 보이면 A** 입니다. 그 경로를 허용 규칙에 넣으면 됩니다.
- 거부 로그가 **없는데** 여전히 실패하면 B 이거나, 로그가 다른 곳(auditd, 별도 로그 파일)에 있는 것입니다. `collect-diag.sh` 는 이를 모두 모읍니다.
- 디스크를 `/home`, `/data` 같은 **비표준 경로**에 두면 libvirt 기본 프로필이 허용하지 않습니다. 기본 경로(`/var/lib/libvirt/images`)를 쓰면 이 문제를 피하기 쉽습니다.

> [!IMPORTANT]
> `security_driver = "none"` 은 AppArmor를 **모든 VM에 대해** 끄는 것이고, 소유권 문제(B)는 해결하지 못합니다. 원인을 확정하지 못한 채 쓰는 임시 우회로만 취급하고, 문서와 논문에는 "해결"이 아니라 "우회"로 적습니다. 이 프로젝트에서는 AppArmor를 켠 채 허용 규칙을 추가하는 방식으로 해결했습니다. ([1단계](ch1_terraform_vm.md) 참고)

## 3. 자동화로 막기: 사전 점검

자동화 코드는 "문제가 생기면 고친다"가 아니라 **"시작 전에 점검하고, 필요한 설정을 먼저 넣는다"** 여야 새 머신에서 한 번에 끝납니다.

```bash
sudo bash scripts/preflight.sh          # 점검만 (KVM, libvirt, 디스크 경로, AppArmor 규칙, 메모리)
sudo bash scripts/preflight.sh --fix    # AppArmor 허용 규칙 추가 (여러 번 실행해도 결과가 같음)
```

키트가 완성되면 이 점검을 `make preflight` 같은 첫 단계로 넣고, 1단계(`terraform apply`) 앞에 둡니다. 실패 시 위 수집 스크립트를 자동 실행해 결과를 남기게 하는 것도 좋습니다.

> [!NOTE]
> **TODO:** `preflight.sh` 는 아직 실제 서버에서 검증하지 않았습니다. 깨끗한 서버에서 `--fix` 없이/있이 각각 실행해 보고 결과를 기록하세요.

## 4. 새 머신 재현 검증

"내 서버에서만 된다"가 아님을 보이는 절차입니다. 논문의 재현성 근거가 됩니다.

1. **깨끗한 서버를 준비**합니다. OS 재설치 직후 상태가 가장 좋습니다. 기존 서버에서 한 수동 설정(AppArmor 규칙 등)이 남아 있으면 안 됩니다.
2. 문서/키트의 명령**만** 순서대로 실행합니다. 중간에 손으로 고치지 않습니다. 고쳐야 했다면 그것이 **문서나 코드의 결함**입니다.
3. 단계마다 아래를 기록합니다.

| 단계 | 소요 시간 | 성공 여부 | 손으로 고친 것 | 실패 시 로그 파일 |
|---|---|---|---|---|
| 0 | | | | |
| 1 | | | | |
| 2 | | | | |
| 3 | | | | |
| 4 | | | | |

4. 실패하면 `collect-diag.sh` 결과를 저장하고, 원인과 해결을 [7장](ch7_troubleshooting.md)에 같은 형식(증상, 원인, 해결, 확인 로그)으로 추가한 뒤 **코드/문서를 고쳐서 처음부터 다시** 돌립니다.
5. 처음부터 끝까지 **손 개입 없이** 통과한 실행 로그를 보관합니다.

환경이 달라질 때 결과가 어떻게 달라지는지 보려면 가능한 한 다음을 바꿔 가며 반복합니다.

| 바꿀 조건 | 이유 |
|---|---|
| 디스크 경로 (기본 경로 / 비표준 경로) | AppArmor·소유권 문제 재현 |
| AppArmor 켬 / 허용 규칙 없음 | 규칙의 필요성을 대조 실험으로 증명 |
| 방화벽 정책 (UDP 123 차단) | 시간 동기화 실패 재현 |
| 서버 재부팅 후 | 재부팅 후 동작 확인 (현재 미확인) |

## 5. 이슈를 기록하는 형식

[7장](ch7_troubleshooting.md)의 각 항목에 아래를 채우면, 비슷한 문제를 겪는 사람이 바로 대조할 수 있습니다.

```text
증상:        (에러 메시지 원문)
환경:        (OS, 버전, 디스크 경로, AppArmor 상태)
확인한 로그:  (명령과 핵심 출력 몇 줄)
원인:        (로그로 확정한 것 / 추정인 것을 구분해서)
해결:        (명령)
해결 확인:    (성공했을 때의 출력)
재현 여부:    (새 머신에서 다시 확인했는가)
```

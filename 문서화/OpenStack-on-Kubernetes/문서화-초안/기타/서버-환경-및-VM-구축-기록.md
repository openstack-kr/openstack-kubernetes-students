# OpenInfra Lab Kit 서버 환경 설정 및 VM 구축 기록

**작성 기준일:** 2026.10.31.

**진행 상태:** 0단계 완료 / 1단계 완료 / 2단계 진행 시작

## 1. 프로젝트 개요

### 1.1. 프로젝트 소개

우리 팀은 OpenStack과 Kubernetes를 처음 접하는 사람들도 클라우드 실습 환경을 쉽게 구축할 수 있도록 **OpenInfra Lab Kit**를 개발하고 있다.

기존에는 Kubernetes나 OpenStack을 설치하려면 여러 도구를 각각 설치하고, 복잡한 설정을 직접 입력해야 한다. 이 과정에서 오류가 발생하면 초보자는 어느 부분이 잘못되었는지 파악하기 어렵다.

따라서 이번 프로젝트에서는 기존 오픈소스 도구들을 연결하여 설치 과정을 자동화하고, 오류가 발생했을 때 문제를 확인할 수 있는 실습 지원 도구를 만드는 것을 목표로 한다.

최종적으로는 다음 세 가지 결과물을 만들 예정이다.

1. 실습 환경을 자동으로 구축하는 코드
2. 초보자가 따라 할 수 있는 RST/Sphinx 기반 가이드북
3. 구축 성공률, 결과 일관성, 자동화 수준에 대한 평가 결과

평가는 자동화하지 않고 팀원들이 직접 반복 실행한 뒤 결과를 정리한다.

### 1.2. 구현 범위

처음에는 두 가지 구조를 모두 고려했다.

- **OpenStack on Kubernetes(OoK):** Kubernetes 위에 OpenStack을 설치하는 구조
- **Kubernetes on OpenStack(KoO):** OpenStack에서 만든 가상머신 위에 Kubernetes를 설치하는 구조

현재는 시간과 구현 난이도를 고려하여 **OpenStack on Kubernetes만 실제로 구현**하기로 했다.

Kubernetes on OpenStack은 구조를 설계하되 실제 구현은 향후 연구로 남긴다.

## 3. 서버 환경 확인

### 3.1. 서버 사양

이번 프로젝트에서는 iwinv에서 대여한 XEON 96T BMv1 베어메탈 서버를 사용하고 있다.

베어메탈 서버는 실제 물리 서버를 직접 사용하는 형태이다. 하나의 물리 서버 안에 여러 대의 가상머신을 만들어 실습할 수 있다.

서버에서 확인한 환경은 다음과 같다.

| 항목 | 확인 결과 |
|---|---|
| 서버 종류 | 베어메탈 |
| 운영체제 | Ubuntu 24.04.1 LTS |
| CPU | Intel Xeon Gold 6262 |
| CPU 스레드 | 96개 |
| 메모리 | 약 125GiB |
| 기본 디스크 | 약 465.8GB |
| 가상화 | KVM 사용 가능 |
| 추가 스토리지 | 250GB 장치 1개 확인, 사용 여부 미정 |

서버 대여 상품에 포함된 것으로 안내된 추가 블록스토리지 4개의 실제 제공 여부는 아직 확인이 필요하다.

### 3.2. 서버 확인에 사용한 명령어

서버가 구축에 적합한지 확인하기 위해 여러 명령어를 사용했다.

**운영체제 확인**

```bash
cat /etc/os-release
```

현재 서버에 어떤 Linux 운영체제가 설치되어 있는지 확인하는 명령어이다.

**CPU 확인**

```bash
lscpu
```

CPU 모델과 코어, 스레드, 가상화 지원 여부 등을 확인할 수 있다.

**메모리 확인**

```bash
free -h
```

전체 메모리와 현재 사용량을 사람이 읽기 쉬운 단위로 보여 준다.

**디스크 확인**

```bash
lsblk
df -h
```

`lsblk`는 디스크와 파티션을 확인하고, `df -h`는 마운트된 파일시스템의 사용량을 확인한다.

**가상화 지원 여부 확인**

```bash
systemd-detect-virt
ls -l /dev/kvm
```

`systemd-detect-virt` 실행 결과는 `none`이었으며, `/dev/kvm` 장치도 존재했다.

따라서 이번 서버는 베어메탈 환경이고 KVM을 사용할 수 있는 것으로 확인했다.

`virsh`는 libvirt에서 가상머신을 조회하거나 관리할 때 사용하는 명령어이다.

## 5. 서버 시간 동기화 문제

### 5.1. 발생한 문제

서버 환경을 점검하는 과정에서 서버 시간이 실제 시간보다 약 6분 빠른 문제가 발견되었다.

처음에는 다음 명령어로 시간 동기화 상태를 확인했다.

```bash
chronyc tracking
```

당시에는 다음과 같은 결과가 나왔다.

```text
Leap status : Not synchronised
```

이 결과는 서버가 NTP 시간 서버와 정상적으로 동기화되지 않았다는 의미이다.

서버의 시간이 정확하지 않으면 나중에 Kubernetes나 OpenStack을 설치할 때 인증서 유효 시간 및 로그 분석 등에 문제가 생길 수 있어 해결이 필요했다.

### 5.2. 원인 확인

확인 결과 서버에는 `chrony`가 실행되고 있었지만, NTP 서버의 응답을 받지 못하고 있었다.

추가로 확인한 내용은 다음과 같다.

- NTP 서버 주소는 정상적으로 확인됨
- 인터넷의 HTTPS 통신은 정상적으로 동작함
- NTP 서버로 보낸 요청은 응답을 받지 못함
- Cloudv ELCAP 방화벽 정책에 UDP 123 포트가 빠져 있었음

NTP는 서버의 시간을 동기화하기 위해 사용하는 프로토콜이며, 일반적으로 UDP 123 포트를 사용한다.

### 5.3. 해결 방법

해당 서버는 iwinv 콘솔이 아니라 Cloudv ELCAP에서 방화벽을 관리하고 있었다.

따라서 Cloudv의 방화벽 정책 중 **나가는 목적지 포트** 목록에 다음 항목을 추가했다.

```text
서비스: ntp
프로토콜: udp
포트: 123
```

이후 시간 동기화가 가능해졌고, 약 366.4초의 시간 오차를 보정했다.

### 5.4. 해결 여부 확인

2026년 10월 31일에 다시 아래 명령어로 확인했다.

```bash
chronyc tracking
```

주요 결과는 다음과 같았다.

```text
Stratum     : 3
Leap status : Normal
```

시스템 시간과 NTP 시간의 차이도 매우 작게 나타났다.

따라서 **현재는 서버 시간 동기화가 정상적으로 유지되고 있는 것으로 확인했다.**

### 5.5. 이번에 알게 된 점

처음에는 시간 동기화 프로그램 자체가 잘못된 것으로 생각할 수 있지만, 실제 원인은 서버 외부의 방화벽 설정이었다.

따라서 앞으로는 시간 동기화 문제가 발생하면 프로그램 실행 여부뿐 아니라 방화벽과 NTP 서버 연결 상태도 함께 확인해야 한다.

이 항목은 나중에 OpenInfra Lab Kit의 환경 점검 기능에 포함할 예정이다.

## 6. 1단계: Terraform으로 VM 4대 구축

### 6.1. VM을 4대 만드는 이유

물리 서버 1대에 Kubernetes와 OpenStack의 모든 구성요소를 설치하는 대신, 내부에 VM 4대를 만들어 각각 다른 역할을 맡도록 구성했다.

이 VM 4대는 팀원 4명이 개인적으로 하나씩 사용하는 서버가 아니다.

**4대가 함께 하나의 Kubernetes 클러스터를 구성하고, 그 위에서 OpenStack을 실행하기 위한 노드**이다.

### 6.2. VM 구성

| VM 이름 | 역할 | vCPU | 메모리 | 디스크 |
|---|---|---:|---:|---:|
| cp | Kubernetes Control Plane | 4 | 16GiB | 60GB |
| ctrl-worker | OpenStack 제어 서비스용 워커 | 16 | 32GiB | 120GB |
| compute-1 | 컴퓨트 워커 | 10 | 32GiB | 80GB |
| compute-2 | 컴퓨트 워커 | 10 | 32GiB | 80GB |
| 합계 | | 40 | 112GiB | 340GB |

각 VM의 역할은 다음과 같다.

**cp**

Kubernetes 클러스터를 전체적으로 관리하는 노드이다. 다른 노드의 상태를 확인하고 클러스터 운영을 담당한다.

**ctrl-worker**

OpenStack의 주요 제어 서비스를 실행할 예정인 노드이다.

**compute-1, compute-2**

OpenStack의 컴퓨팅 기능을 담당할 예정인 노드이다.

현재는 VM 생성이 완료된 상태이며, Kubernetes와 OpenStack 서비스까지 설치된 것은 아니다.

### 6.3. 네트워크 구성

VM 4대가 서로 통신할 수 있도록 libvirt의 가상 네트워크를 구성했다.

- 네트워크 이름: `openinfra-lab`
- 네트워크 대역: `192.168.100.0/24`
- 통신 방식: NAT
- IP 할당 방식: MAC 주소와 IP를 연결한 DHCP 고정 예약

각 VM의 IP는 다음과 같이 설정했다.

| VM 이름 | 내부 IP |
|---|---|
| cp | 192.168.100.10 |
| ctrl-worker | 192.168.100.11 |
| compute-1 | 192.168.100.21 |
| compute-2 | 192.168.100.22 |

여기서 사용하는 IP는 서버 내부의 가상 네트워크 주소이며, 서버의 공인 IP와는 다르다.

고정 IP로 구성한 이유는 Kubernetes 설치 시 각 노드가 일정한 IP 주소를 사용해야 하고, 환경을 다시 만들더라도 동일한 구성이 나오도록 하기 위해서이다.

### 6.4. Terraform 코드 구성

현재 VM 구축에는 다음 파일을 사용했다.

```text
~/openinfra-lab-kit/
└── terraform/
    ├── versions.tf
    └── main.tf
```

- `versions.tf`: Terraform과 libvirt provider 버전을 관리하는 파일
- `main.tf`: VM, 디스크, 네트워크 등을 정의한 파일

Terraform을 사용하면 VM을 하나하나 수동으로 만드는 대신 설정 파일에 필요한 자원을 적어 두고 한꺼번에 생성할 수 있다.

현재 구성에서는 저장 풀, 네트워크, 디스크, cloud-init, VM 등을 합쳐 총 19개의 Terraform 자원을 사용했다.

VM의 초기 설정에는 `cloud-init`을 사용했으며, VM 접속용 계정과 SSH 키, 호스트명 등을 설정했다.

### 6.5. Terraform 실행 과정

기록된 주요 실행 순서는 다음과 같다.

```bash
terraform fmt
terraform validate
terraform plan -out=tfplanN
terraform apply tfplanN
```

각 명령어의 의미는 다음과 같다.

| 명령어 | 의미 |
|---|---|
| `terraform fmt` | Terraform 코드의 형식을 정리 |
| `terraform validate` | 코드의 문법과 설정이 올바른지 확인 |
| `terraform plan` | 실행하면 어떤 자원이 생성·변경되는지 미리 확인 |
| `terraform apply` | 실제로 VM 등의 자원을 생성하거나 변경 |

`tfplanN`은 실제 작업에서 저장한 계획 파일의 예시 이름이다.

최종 성공한 `apply` 실행에서는 VM 4대가 생성되었고, 소요 시간은 약 **1분 30초**로 기록되었다.

단, 이 시간은 오류를 해결한 후 성공한 실행에 걸린 시간이며, 전체 문제 해결 시간까지 포함한 것은 아니다.

### 6.6. VM 실행 상태 확인

10월 31일 SSH로 서버에 접속하여 다음 명령어를 실행했다.

```bash
virsh -c qemu:///system list --all
```

확인 결과:

```text
 Id   Name          State
----------------------------
 1    compute-1     running
 2    ctrl-worker   running
 3    compute-2     running
 4    cp            running
```

4대 모두 `running`으로 표시되어 정상적으로 실행 중인 것을 확인했다.

또한 구축 기록에서는 다음 사항도 확인되었다.

- VM 4대에 계획한 고정 IP가 할당됨
- SSH 키를 이용하여 4대 모두 접속 가능
- 각 VM의 호스트명이 정상적으로 설정됨
- VM의 시간 동기화가 정상적으로 동작함

따라서 **Terraform을 이용한 VM 4대 생성과 기본 접속 확인은 완료**된 것으로 정리했다.

다만 실제 Kubernetes 클러스터 구축 여부는 다음 단계에서 별도로 확인해야 한다.

## 7. VM 구축 중 발생한 오류

### 7.1. Terraform provider 문법 문제

처음 참고한 인터넷의 Terraform 예제 중 일부가 현재 설치한 libvirt provider 버전과 맞지 않는 문제가 있었다.

현재 사용하는 `dmacvicar/libvirt` provider 0.9.9는 이전 버전과 설정 문법에 차이가 있다.

따라서 인터넷 예제를 그대로 사용하는 대신 다음 명령어를 이용해 현재 버전의 설정 구조를 확인했다.

```bash
terraform providers schema -json
```

이 과정에서 디스크 형식이나 네트워크 고정 IP 설정 방법 등을 현재 버전에 맞게 수정했다.

**알게 된 점:** Terraform은 같은 provider라도 버전에 따라 설정 방법이 달라질 수 있으므로, 사용할 버전을 먼저 정하고 해당 버전의 문서를 확인해야 한다.

### 7.2. cloud-init ISO 형식 문제

Terraform의 `plan` 결과에서 cloud-init ISO 볼륨이 계속 변경 대상으로 표시되는 문제가 있었다.

처음에는 해당 볼륨의 형식을 `raw`로 설정했지만, libvirt에서는 `.iso` 파일을 `iso` 형식으로 인식하고 있었다.

따라서 볼륨의 형식을 `iso`로 수정하여 불필요한 변경이 반복되는 문제를 해결했다.

### 7.3. AppArmor로 인한 VM 실행 실패

VM 구축 과정에서 가장 크게 문제가 되었던 부분이다.

Terraform으로 VM 관련 자원을 생성했지만, 실제 VM을 시작하는 과정에서 다음과 같은 오류가 발생했다.

```text
Could not open '...base.qcow2': Permission denied
```

`Permission denied`는 프로그램이 필요한 파일이나 자원에 접근하지 못했다는 의미이다.

확인 과정에서는 다음 항목들을 점검했다.

1. VM 4대를 동시에 실행해서 생긴 문제인지 확인
2. VM을 순서대로 실행해도 같은 문제가 발생하는지 확인
3. 기준 이미지와 디스크 파일의 상태 확인
4. 파일 접근 권한 확인
5. VM 이미지 저장 위치 변경
6. AppArmor 관련 설정 확인

이 과정에서 VM 시작을 순차적으로 변경하거나 저장 위치를 바꾸어도 오류가 계속 발생했다.

반면 libvirt의 VM별 보안 드라이버를 비활성화한 뒤에는 같은 구성으로 VM 생성이 성공했다.

따라서 **libvirt의 AppArmor 보안 격리가 VM 시작 실패와 관련된 원인으로 판단**했다.

다만 구체적으로 어떤 AppArmor 규칙이 기준 이미지 접근을 막았는지는 확인하지 못했다.

#### AppArmor란?

AppArmor는 Linux에서 프로그램이 접근할 수 있는 파일이나 기능을 제한하는 보안 기능이다.

프로그램이 허용되지 않은 작업을 수행하려고 하면 접근을 차단하여 시스템을 보호한다.

이번 프로젝트에서는 가상머신 실행 프로그램이 디스크 이미지를 읽는 과정에서 제한이 발생한 것으로 판단했다.

#### 적용한 임시 해결 방법

호스트의 `/etc/libvirt/qemu.conf` 파일에 다음 설정을 추가했다.

```ini
security_driver = "none"
```

이 설정은 libvirt가 VM별로 적용하는 추가 보안 격리를 비활성화한다.

설정을 변경한 뒤 관련 서비스를 재시작하고 Terraform을 다시 적용하여 VM을 생성했다.

#### 현재 보안 상태 확인

10월 31일 다음 명령어를 실행하여 호스트의 AppArmor 상태를 확인했다.

```bash
sudo aa-status
```

결과:

```text
apparmor module is loaded.
16 profiles are loaded.
16 profiles are in enforce mode.
```

이는 Ubuntu 전체의 AppArmor가 비활성화된 것이 아니라, 호스트에 여러 AppArmor 보안 프로필이 여전히 적용되고 있다는 의미이다.

또한 다음 명령어로 libvirt 설정 파일을 확인했다.

```bash
sudo grep -nE '^[[:space:]]*security_driver[[:space:]]*=' /etc/libvirt/qemu.conf
```

결과:

```text
1003:security_driver = "none"
```

따라서 현재 설정 파일에는 libvirt의 VM별 보안 드라이버를 사용하지 않도록 하는 설정이 들어 있는 것을 확인했다.

**주의할 점**

이 방법은 VM 실행 문제를 우회하기 위한 임시 조치이며, 보안 수준이 낮아진다는 한계가 있다.

실제 운영 환경에 그대로 적용하는 것은 권장하지 않는다.

현재 멘토님께 해당 설정을 실습용으로 유지해도 되는지 질문한 상태이며, 향후 AppArmor의 필요한 규칙만 수정하는 방법도 검토할 예정이다.

### 7.4. 기타 Terraform 오류

구축 과정에서 다음 오류도 발생했다.

| 오류 또는 문제 | 확인한 내용 및 해결 |
|---|---|
| Ubuntu 이미지 다운로드 경로 변경 | 날짜별 Noble 이미지 경로 사용 |
| `plan`에서 ISO가 계속 변경됨 | 볼륨 형식을 `iso`로 수정 |
| 저장 풀 경로 변경 후 상태 불일치 | 관련 자원을 정리한 후 새 경로로 재생성 |
| `Saved plan is stale` | 변경된 상태에 맞춰 계획 파일을 새로 생성 |
| VM 시작 `Permission denied` | AppArmor 관련 설정을 임시 변경하여 우회 |

이처럼 실제 구축 과정에서는 예상하지 못한 문제가 여러 번 발생했다.

앞으로 자동화 키트를 만들 때에는 이런 오류를 단순히 무시하지 않고, **어느 단계에서 어떤 문제가 발생했는지 안내할 수 있도록 하는 것이 중요하다.**

## 8. SSH 접속 및 작업 환경

### 8.1. 서버 접속 방식

팀원들은 각자의 노트북에서 SSH를 이용해 하나의 물리 서버에 접속하여 작업하고 있다.

서버 작업용 계정과 VM 내부 접속용 계정은 구분되어 있으며, SSH 키를 이용하여 접속하도록 설정했다.

여러 명이 동시에 서버에 접속하는 것은 가능하지만, 동일한 자원을 동시에 수정하는 것은 주의해야 한다.

예를 들어 두 명이 같은 Terraform 디렉터리에서 동시에 `terraform apply`를 실행하면 작업이 충돌할 수 있다.

따라서 앞으로는 각 단계의 실행 담당자를 명확하게 정할 필요가 있다.

### 8.2. SSH 접속 불가 문제

10월 30일 저녁에는 한 팀원의 컴퓨터에서 서버에 SSH로 접속하지 못하는 문제가 발생했다.

당시 나타난 오류는 다음과 같다.

```text
ssh: connect to host ... port 22: Operation timed out
```

하지만 접속이 다시 가능해진 후 확인했을 때, 서버가 해당 시간 동안 재부팅된 흔적은 없었다.

따라서 서버 자체가 종료되었다기보다는 네트워크 경로나 방화벽과 관련된 문제일 가능성이 있었다.

정확한 원인과 복구 방법은 아직 확인하지 못했다.

### 8.3. 작업 시 주의사항

- 조원들이 사용 중인 VM을 임의로 종료하거나 삭제하지 않는다.
- Terraform 변경 작업은 실행 담당자를 정한 뒤 진행한다.
- 서버 설정을 변경하기 전 팀원들에게 공유한다.
- SSH 개인키와 비밀번호를 GitHub에 올리지 않는다.
- 서버의 공인 IP와 접근 관련 정보는 외부에 공개하지 않는다.
- 오류 메시지와 해결 방법은 가능한 한 당시의 기록을 바탕으로 정리한다.

## 9. 2단계: Ansible 노드 사전 설정

현재는 VM 4대 생성이 끝나고 Ansible을 이용한 노드 사전 설정을 시작했다.

Ansible은 여러 서버에 동일한 작업을 한 번에 실행할 수 있도록 도와주는 자동화 도구이다.

예를 들어 VM 4대에 동일한 패키지를 설치하거나 네트워크 설정을 변경해야 할 때, 각 VM에 일일이 접속하는 대신 Ansible을 사용할 수 있다.

### 9.1. 현재 준비한 내용

Ansible 설정을 위해 다음 파일을 준비했다.

```text
~/openinfra-lab-kit/
└── ansible/
    ├── inventory.ini
    └── ansible.cfg
```

- `inventory.ini`: 관리할 VM 목록과 IP, 역할을 작성하는 파일
- `ansible.cfg`: Ansible 접속 계정, SSH 키, 인벤토리 위치 등을 설정하는 파일

### 9.2. 앞으로 확인할 항목

| 확인 항목 | 목적 | 진행 상태 |
|---|---|---|
| Ansible ping | VM 4대에 접속되는지 확인 | 확인 예정 |
| swap 비활성화 | Kubernetes 설치 준비 | 설정 필요 |
| 커널 모듈 | 컨테이너 네트워크 준비 | 설정 필요 |
| IP 포워딩 | 네트워크 패킷 전달 | 설정 필요 |
| `/etc/hosts` | 노드 간 이름 확인 | 점검 필요 |
| 시간 동기화 | 각 VM의 시간 정확도 확인 | 동기화 확인, 서버 출처 추가 확인 필요 |
| 기본 패키지 | 이후 단계 설치 준비 | 점검 필요 |

Ansible 연결 확인에 사용할 명령어는 다음과 같다.

```bash
ansible all -m ping
```

이 명령어는 일반적인 네트워크 ping과 달리, Ansible이 대상 VM에 접속해서 모듈을 실행할 수 있는지 확인하는 데 사용한다.

현재 참고한 구축 기록에서는 아직 이 명령어의 성공 결과가 확인되지 않았다.

따라서 **2단계는 완료가 아니라 시작 단계**로 기록한다.

## 12. 정리 및 느낀 점

이번 구축을 진행하면서 단순히 프로그램을 설치하는 것보다 **설치에 필요한 환경을 미리 확인하는 과정이 중요하다**는 것을 알게 되었다.

예를 들어 처음에는 서버의 시간 동기화가 되지 않는 원인을 정확히 알기 어려웠지만, 하나씩 확인해 보니 방화벽의 UDP 123 포트가 문제라는 것을 찾을 수 있었다.

또한 Terraform으로 VM을 생성하는 과정에서도 코드 문법이나 디스크 파일 권한 등 여러 문제가 발생했다.

특히 AppArmor 문제는 설정을 변경하여 VM 실행에는 성공했지만, 보안 기능을 일부 비활성화했다는 한계가 남아 있다.

이러한 문제들을 기록해 두면 앞으로 같은 오류가 발생했을 때 다시 처음부터 원인을 찾지 않아도 될 것 같다.

우리 프로젝트의 목표는 단순히 Kubernetes와 OpenStack을 설치하는 것이 아니라, **처음 사용하는 사람도 구축 과정에서 발생할 수 있는 문제를 이해하고 해결할 수 있도록 돕는 것**이다.

따라서 앞으로도 각 단계에서 사용한 명령어와 실행 결과, 오류 및 해결 방법을 정리하고 이를 최종 입문자용 가이드북에 반영할 예정이다.
